# The self-hosted Axiom compiler

A port of the C compiler in [`compiler/`](../compiler/README.md) to Axiom, with its own
code generation. The front end has the same command line and prints byte-identical
diagnostics for every program in the repository. The back end does not use LLVM: the
compiler lowers programs to its own SSA IR, optimizes it, and generates WebAssembly
(wasm32, wasm64), x86-64 or AArch64 code, which its own linkers turn into `.wasm` modules
and Linux executables. The compiler, and the programs it builds, need nothing but the C
library: no LLVM, no C compiler, no `ld` or `wasm-ld`. (A C toolchain is used only to
compile C sources that a program links in.)

It also has the formatter, `axiom fmt` (spec §16.5), which the C compiler does not:

```
$ axiom fmt <file.ax | dir>... [--check] [--stdout]
```

It rewrites each file (every `.ax` file under a directory) in the canonical layout and
tidies its imports: each run of imports is sorted by path, duplicate and unused imports
are removed (except a package import, or a module with tests, since importing it runs
them), and a standard library module used as `name.x` but never imported is added.
`--check` changes nothing: it lists the files that are not canonical and exits with 1 if
there are any. `--stdout` prints the result instead. A file with a syntax error is
reported and left alone, and so is one whose formatted text would not lex to the same
tokens and comments (an internal error). The repository's sources are kept canonical
(`tests/run.mjs` checks them, and the examples in `tests/fmt`).

## Bootstrapping

```
$ selfhost/bootstrap.sh
```

| Stage | Compiler | Built by |
|---|---|---|
| 0 | `compiler/build/axiom` (C, uses LLVM) | `make -C compiler` |
| 1 | `selfhost/build/axiom1` (code generated by LLVM) | stage 0 |
| 2 | `selfhost/build/axiom2`, copied to `selfhost/build/axiom` | stage 1 |
| 3 | `selfhost/build/axiom3` | stage 2 |

The script fails unless stages 2 and 3 are bit-identical (the fixed point). Stage 1 is
the only one LLVM is involved in; from stage 2 on, the compiler builds itself. `OPT=-O0`
builds the stages without optimization, which is faster. `CROSS=1` also builds stage 2
for the other architecture and checks, under qemu, that it generates exactly the same
code.

To build the compiler by hand with any existing Axiom compiler:

```
$ axiom build selfhost/src/main.ax --target=native -O2 -o axiom
```

`selfhost/build/axiom` finds the standard library and the runtime the same way the C
compiler does (`../../std` from the executable, or `--std`, or `$AXIOM_STD`).

## Targets and processor extensions

```
--target=wasm32 | wasm64 | x86_64 | aarch64 | native      (default wasm32)
--cpu=<preset>
--features=+ext,-ext
```

| Target | `--cpu` presets | Extensions (`--features`) |
|---|---|---|
| wasm32, wasm64 | `mvp`, `generic` (default), `bleeding-edge` | `simd128`, `bulk-memory`, `nontrapping-fptoint`, `sign-ext`, `mutable-globals`, `atomics`, `multivalue`, `relaxed-simd`, `tail-call` |
| x86_64 | `x86-64` (= `generic`), `x86-64-v2`, `x86-64-v3`, `x86-64-v4`, `native` | `sse3`, `ssse3`, `sse4.1`, `sse4.2`, `popcnt`, `lzcnt`, `bmi`, `bmi2`, `avx`, `avx2`, `fma`, `cx16` |
| aarch64 | `armv8-a` (= `generic`), `armv8.1-a`, `armv8.2-a`, `armv8.3-a`, `apple-m1`, `neoverse-n1`, `native` | `lse`, `rcpc`, `dotprod`, `cssc` |

`--target=native` means this machine's architecture with `--cpu=native` (its extensions,
from `/proc/cpuinfo`); `--target=x86_64` and `--target=aarch64` default to the baseline.
Without an extension the backends use a baseline sequence with the same result, so the
choice never changes what a program computes:

- **wasm**: SIMD and threads (shared memory) are checked against `simd128` and `atomics`.
- **x86-64**: SSE2 is the baseline. SSSE3 (`pshufb` shuffles, `pabs`), SSE4.1 (rounding,
  `pmulld`, `pextr`/`pinsr`, 64-bit lane equality, min/max), SSE4.2 (64-bit lane
  compares), POPCNT, LZCNT, BMI1 (`tzcnt`), BMI2 (`shlx`...), AVX (three-operand VEX
  encoding of all SSE instructions) and FMA are used when enabled.
- **AArch64**: the FP and Advanced SIMD (NEON) baseline covers everything; LSE replaces
  the load-exclusive / store-exclusive loops of atomic read-modify-write and
  compare-and-swap with single instructions.

Programs for another architecture are linked without a cross toolchain. `axiom test`
and `axiom profile` run them under `qemu-<arch>` (with the target's C library from
`/usr/<arch>-linux-gnu`) when the target is not the machine's.

## How code is generated

| Module | What |
|---|---|
| `ir.ax` | The SSA IR: types, values, instructions, blocks, functions, globals; a builder that folds constants; a printer (`--emit=ir`) |
| `codegen.ax` | The checked program to IR (monomorphization, traps, the shadow stack for stack traces) |
| `lower.ax` | Target-independent lowering: aggregates to memory, the internal calling convention (aggregates of up to four scalars as those scalars, larger ones by pointer, results through an sret pointer), and splitting vector operations a target cannot do into lanes |
| `passes.ax` | The optimization pipeline (below) |
| `opt.ax` | mem2reg (SSA construction), constant folding, CFG simplification, dead code elimination; dominators, loops, critical edge splitting; code layout (loops contiguous, exit tests after the body, trap paths last) and constants hoisted out of loops for the native backends |
| `combine.ax` | Instruction combining: algebraic identities, canonical forms, comparisons (constant ranges, extensions, the forms overflow checks take), narrowing, loads of constants |
| `sroa.ax` | Scalar replacement of aggregates: stack slots split into scalar fields, copies of constants replaced by the constant |
| `gvn.ax` | Global value numbering over the dominator tree with memory (redundant loads, store-to-load forwarding, alias analysis), facts from branch conditions and bounds between values (bounds and overflow checks), dead stores, shadow stack pushes and pops (and their records moved to the paths that read them), loop-invariant code motion, memset idioms, loop ranges split at bounds checks, code sinking |
| `thread.ax` | Jump threading and if-conversion (selects; stores in both arms merged) |
| `inline.ax` | Inlining bottom-up over the call graph (and the calls inlining brings in), interprocedural constant propagation, dead functions |
| `outline.ax` | Cold region outlining: the uncommon path of a small function that makes calls moves into a function of its own |
| `wasm.ax`, `wobj.ax` | WebAssembly: structured control flow from the CFG, stackification, the encoder, relocatable object files (the same format as LLVM's) |
| `wlink.ax` | The wasm linker: memory layout, function table, exports, shared memory for threads |
| `mach.ax` | Machine IR shared by the native backends, liveness and linear-scan register allocation with spilling, redundant reloads and spill stores removed |
| `x64.ax`, `x64enc.ax` | x86-64 instruction selection (System V ABI; loads folded into memory operands), frame layout, encoding |
| `a64.ax`, `a64enc.ax` | AArch64 instruction selection (AAPCS64), frame layout, encoding |
| `elf.ax` | ELF relocatable objects: writing, and reading them back for the linker |
| `elink.ax` | The ELF linker: a static executable when nothing needs the C library, otherwise a dynamically linked one against `libc.so.6` (own `_start`, PLT and GOT, symbol versions, thread-local storage, a symbol table for debuggers and profilers) |
| `lstub.ax` | Machine code the linker supplies: the system call and thread-creation stubs, the signal return trampoline, the static `_start`, and `memcpy`/`memmove`/`memset` on AArch64 |
| `target.ax` | Architectures, CPU presets, extensions, host detection |
| `backend.ax` | Lowering, optimization and the target's code generator |

Native programs include the runtime written in Axiom, which uses no C library:
`runtime/linux.ax` (system calls on x86-64 and AArch64), `runtime/native.ax` (the host
ABI used by `std/io`, `std/net` and threads, a DNS resolver, crash reports with stack
traces),
`runtime/test_main.ax` (the forking test runner of `axiom test`),
`runtime/profile.ax` (the sampling profiler of `axiom profile`) and `runtime/rt.ax`
(software `fmod` and `fma` where the target has no instruction).

## Testing

```
$ AXIOM=selfhost/build/axiom node tests/run.mjs     # the whole suite, any options
$ node tests/std_opt.mjs                             # std's tests at -O2 on both targets, with checks
$ selfhost/difftest.sh                                    # compare with the C compiler
$ selfhost/fuzz/run.sh 1 20                               # backends vs LLVM on random programs
$ selfhost/build/axiom test selfhost/src/util.ax --target=native
```

`std_opt.mjs` builds and runs every std module's tests at `-O2` (or the level given)
for wasm32 and native, one module per job, with `AXIOM_CHECK_CINTS=1` (no pass changes a
shared constant) and `AXIOM_POISON=1` (released memory is poisoned, never reused). Run it
after changing the optimizer or a backend: the std tests are the largest programs the
suite has. With `--sanitize=address` (and a longer `--test-timeout=ms`: the
sanitizer makes code 3–4 times slower) it also checks every std test for memory errors
and leaks.

`difftest.sh` checks every `.ax` file under `tests/`, `std/`, `examples/` and
`selfhost/src/` for identical diagnostics (`check --format=agent-json`) and exit status,
runs the test suite for wasm32 and native code at `-O0` and `-O2` and in whole-program
mode (and for AArch64 under qemu when available), and fuzzes the backends. The fuzzer
(`fuzz/gen.py`) writes programs that apply every integer, floating point and SIMD
operation to edge values; the output of every backend and extension level must match the
C compiler's LLVM-generated code exactly.

The test suite can run AArch64 code on an x86-64 machine:

```
$ AXIOM=selfhost/build/axiom AXIOM_NATIVE_TARGET=aarch64 \
  AXIOM_NATIVE_EXEC="qemu-aarch64 -L /usr/aarch64-linux-gnu" node tests/run.mjs --native
```

(`apt install qemu-user libc6-arm64-cross gcc-aarch64-linux-gnu`; the C compiler is for
the suite's C host functions.) `AXIOM_DUMP_IR=<file>` makes the compiler write the
optimized IR of each compilation, for debugging.

## Optimization

`-O0` runs mem2reg, constant folding, CFG simplification and dead code
elimination. `-O1` adds, per function: instruction combining, jump threading,
if-conversion, scalar replacement of aggregates, global value numbering,
dead store elimination, shadow stack push/pop removal, memset idioms,
loop-invariant code motion and code sinking. `-O2` and `-O3` add cold
region outlining, interprocedural constant propagation and inlining
(whole-program units by default), after which each function is simplified
again, and then split loop ranges at their bounds checks. The backends
then lay out loops, hoist constants, fold loads into memory operands
(x86-64) and allocate registers with live ranges that have holes.

If-conversion keeps a branch when the chosen value goes into the address of
a load (a heap or tree walk), where a predicted branch lets the load start
early.

The shadow stack for stack traces is ordinary memory to the optimizer, with
two facts it may use: the program never computes a pointer to it, and every
call leaves its depth as it found it. A call site's record is written just
before the calls and traps that can read it, so the common path of an
inlined function with a slow path writes none. Traps, stack traces and
error return traces are the same at every optimization level
(tests/traces).

`selfhost/bench.sh` compares the code with LLVM's: the compiler built by
LLVM against the compiler built by itself on the same job, and the programs
in `selfhost/bench/` (sieve, hash map, sorting, matrix and n-body, word
counting) built by both compilers.

## Layout of the front end

The front end's modules follow the C sources. Axiom forbids import cycles, so the mutually
recursive parts of the C semantic analysis are one module, and the AST and the semantic
types share a module.

| Module | C source | What |
|---|---|---|
| `util.ax` | `util.c` | the system (host ABI and std: memory, files, processes), arenas (permanent, and per-function scratch the backends release), `List[T]`, interned strings, `SymMap[V]`, `I128`, formatting, merge sort, files, spans |
| `diag.ax` | `diag.c` | diagnostics, human and agent-json output |
| `lexer.ax` | `lexer.c` | tokens |
| `ast.ax` | `ast.h`, `types.h`, `builtins.h` | syntax tree, semantic types, builtin table |
| `parser.ax` | `parser.c` | LL(1) parser, operator partial order |
| `types.ax` | `types.c` | hash-consed types, substitution, printing, layout, constraints |
| `package.ax` | `package.c` | `axiom.toml`, `pkg:` imports, git dependencies |
| `sema.ax` | `sema_decl.c`, `sema_expr.c`, `sema_builtins.c`, `sema_stmt.c` | module loading, name resolution, type checking |
| `codegen.ax` | `codegen.c` | IR generation (see above), monomorphization, traps, shadow stack |
| `header.ax` | `header.c` | C headers for `export fn`s |
| `units.ax` | `units.c` | separate compilation and the object cache |
| `main.ax` | `main.c` | the driver: `build`, `check`, `test`, `profile`, `new`, `cache`; linking |
| `fmt.ax` | | `axiom fmt`: canonical layout from the token stream, imports tidied |

## How C idioms map to Axiom

- **NULL.** Pointers are non-nullable in the type system, so a C `NULL` is a pointer
  with address 0: `u.nil.[T]()` makes one and `u.isnil(p)` / `u.notnil(p)` test for it.
  An absent string is a slice with a 0 pointer (`u.nosym()`, `u.isnos(s)`).
- **Strings** are `[]u8`. Every string the compiler creates is followed by a NUL in
  memory, so `.ptr` can go to C. Interned strings (`u.intern`) compare by pointer
  (`u.same`).
- **Enums** are `i32` constants, and `switch` statements are `if`/`else if` chains,
  because `match` patterns must be literals.
- **`printf`**: messages are built with `u.f1` ... `u.f6`, which substitute `%s` only.
  Numbers are converted first (`u.idec`, `u.dec`, `u.udec`, `u.zdec`); `u.ffmt` formats
  one float with `snprintf`.
- **`__int128`** constant folding uses `u.I128`, a two's complement 128-bit integer with
  C's truncating division and wrapping multiplication.
- **`qsort`** is `u.sort`, a stable merge sort, like glibc's `qsort` for these arrays.
- **Processes** use `fork` / `execvp` / `waitpid` instead of `posix_spawn`, whose
  argument structures are platform-specific.
- **Evaluation order.** C leaves the order of function arguments unspecified, and GCC
  evaluates nested builder calls right to left, which decided the order of the emitted
  instructions when the port produced the same LLVM IR as the C compiler. Axiom
  evaluates left to right, so where the C code nests two instruction-building calls in
  one argument list, the port still builds them in the order GCC does. Those places are
  marked with a comment.

## Platform assumptions

- Linux on x86-64 or AArch64, or WebAssembly. The compiler reaches the system only
  through the Axiom host ABI and std (spec §15.2), so natively it is a static
  executable that needs no C library, and it also builds for wasm32:

  ```
  selfhost/build/axiom build selfhost/src/main.ax --target=wasm32 -O2 -o axiom.wasm
  node runtime/host.mjs axiom.wasm -- build app.ax --std=std -o app.wasm
  ```

  It produces the same bytes on either host. Where the host cannot fork (node), it
  compiles a program as one unit instead of compiling modules in parallel. It reads
  `/proc/cpuinfo` for `--cpu=native` and `/proc/self/exe` (or, on WebAssembly, its
  module's path) to find std and to key its object cache.
- Programs it builds use only the Linux system call interface and are static, unless
  they link C code or libraries (`-l`, `.c`/`.o` inputs). Those are dynamically linked:
  they use the dynamic loader at its standard path (`/lib64/ld-linux-x86-64.so.2`,
  `/lib/ld-linux-aarch64.so.1`), find `libc.so.6` in the usual library directories, and
  start threads with `pthread_create`.
